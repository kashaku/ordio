# 后续开发路线图

本文件只记录待做事项和验收标准。当前实现见[开发说明](uniapp-mvp-development.md)，已部署资源见 [CloudBase 文档](cloudbase-development.md)。历史验证保存在[开发日志](../dev-log.md)。

目标仍是单店堂食可试营业：顾客扫码、浏览品牌主页和菜单、下单；商家独立登录、发布内容、接单和处理订单。所有核心金额、权限和订单状态最终由服务端决定。多门店字段从一开始保留，首轮不扩展配送、会员或营销。

## 已确定的开发方向

- 顾客使用现有 uni-app 微信小程序，商家使用独立响应式 Web 管理端。
- 主页采用三类模板、品牌色和标准区块，不做自由画布或脚本注入。
- 当前 CloudBase 文档型数据库承载已有身份、门店、桌台和主页配置。继续开发按实际集合与 SDK 进行。
- MySQL 是早期规划的候选方案，尚未落地。订单阶段若决定采用 MySQL，应先确定事务需求、迁移和回滚方案，不能边写文档边默认已经换库，也不长期维护两套订单主数据。
- 保持现有源码目录，暂不引入未使用的 monorepo 子项目。

## A. 完成云端主页这一批

1. 按实时状态补缺失索引，部署并联调新版 `ordioApi`。
2. 保存试点草稿、验证旧 revision 冲突、生成首个发布版本，并读回核对。
3. 顾客主页服务层接 `storefront.getPublished`；无发布版和网络失败给出明确状态，未配置云环境时保留本地开发路径。
4. 修正顾客主页的本地桌台依赖；后续逐步把菜单、结算和下单桌台校验统一到服务端。
5. 临时停用 A02 验证 `TABLE_DISABLED`，无论验证结果如何都恢复并读回启用状态。

验收：顾客只读发布版；未发布编辑不影响顾客；有效发布、未发布门店、网络失败都有可复现页面结果；两个前端构建和已有测试通过。当前顺序修订检查还需补原子并发控制，发布要补重复请求和部分失败恢复；不能仅凭一次顺序联调宣称发布可靠性已完成。

## B. 商家身份、菜单和正式桌码

- 正式网页登录方案仍为 blocker：核对官方身份能力、账号条件、域名和回调，以及 Cookie、CSRF、跨域和退出流程。开发预览身份不进入生产。
- 实现已有 Web service 所约定的 HTTP 接口；云函数动作与 Web HTTP 路由是两层，不能只配置环境变量就视为接通。
- 菜单、菜品、规格、图片迁移到云端；发布形成版本，服务端验证资源和招牌菜归属。
- 实现云端桌台管理、小程序码生成、云存储、下载打印和令牌轮换。具体官方 API 和参数限制在接入时查证。
- 管理端补齐菜单与桌台后，移除旧小程序商家路由及不再需要的本地编辑代码。

验收：商家发布后另一设备能读到；未授权用户无法访问草稿或写接口；员工不能跨店；新旧桌码、停用、未发布菜单、弱网状态均正确；顾客包不含商家工作台。

## C. 服务端订单

- 重新计价、桌台与门店校验、数量和规格校验。
- 幂等订单创建、事务、库存或售罄检查，保存商品价格及桌台快照。
- 本人订单读取、商家接单和履约状态变更，操作记录可追溯。
- 根据查询需要设计订单、订单项、事件、幂等记录；这些资源目前没有部署。

目标履约状态为 `pending_payment → placed → accepted → preparing → ready → completed`，拒单和取消另设分支；支付状态独立维护。当前本地 `pending/paid` 不等于该状态机已实现。

验收：两台设备并发下单不重复、不串店；客户端改价无效；订单跨设备恢复；历史订单不被后续菜单修改改变；商家与顾客状态一致。

## D. 支付、运维与试营业

真实支付、商户号、预支付、通知、查单、退款和对账另行接入，需要账号资质和明确授权。支付结果由服务端确认，不能沿用本地 `payOrder` 作为收款结果。

上线前补开发/预发布/生产隔离、域名和数据库权限核验、日志告警、备份恢复、失败重试、弱网与前后台切换测试。先核查依赖审计和实际可升级组合，不使用破坏 DCloud 版本组的强制修复。

验收：重复通知不重复记账，漏通知能恢复，故障可追踪与恢复；至少完成一次真实门店连续试营业验证。

## 后续候选

门店效率：外带、取餐号、备注、库存、厨房看板、打印、营业时间、日结。经营功能：会员、优惠券、复购、多店、主题包、定时发布和回滚。平台化：入驻、套餐、结算和外部系统集成。均待前述基础完成后按真实需求排期。
