# Ordio 真实运营版优化路线图

本文基于 2026-10-09 已完成的本地 MVP。当前版本已经跑通真机预览，并补充了本地模板化主页搭建骨架，但仍属于单设备开发版本：商家工作台尚未拆出独立管理端、本地缓存充当数据源、订单由客户端创建、付款为模拟状态。

下一阶段不建议直接堆优惠券、会员等功能。先完成身份、权限、云端数据、订单状态和支付闭环，达到单店可真实运营，再扩展多店和营销能力。

## 1. 产品目标

第一目标是完成一个真实餐饮门店可以试营业的版本：

- 顾客扫桌码进入门店，浏览商家主页、当前菜单并下单
- 每个商家可以从行业模板出发，配置视觉、文案、内容区块和招牌菜
- 商家实时接单、拒单、制作、出餐和完成订单
- 菜单、订单和用户数据跨设备同步
- 所有金额、库存、权限和支付结果由服务端确认
- 店主可以管理员工、菜单、桌台和营业状态
- 系统具备日志、备份、告警和问题追踪能力

首个运营版本按单店验收，但数据库从一开始保留 `store_id`，避免以后支持多门店时整体重写。

暂不作为首发阻塞项：配送调度、复杂会员等级、连锁总部结算、发票、广告推荐、开放平台和第三方 SaaS 接口。

## 2. 当前版本与目标版本

| 维度 | 当前 MVP | 真实运营目标 |
| --- | --- | --- |
| 客户端 | 商家和顾客共用一个小程序 | 顾客小程序、商家管理端分离 |
| 身份 | 无登录、无角色 | 微信身份、员工账号、门店角色权限 |
| 数据 | `uni.setStorageSync` 本机缓存 | 云端数据库为唯一业务数据源 |
| 图片 | 本机持久文件 | 云存储文件 ID、压缩图和访问权限 |
| 门店主页 | 本地三模板、品牌色、四类区块和草稿发布 | 云端模板、品牌令牌、可编排区块、发布审计和版本回滚 |
| 菜单 | 本机草稿和发布副本 | 云端草稿、不可变发布版本、发布审计 |
| 桌码 | 二维码内直接保存 `storeId` | 每桌独立且不可猜测的 `tableToken` |
| 订单 | 客户端生成并保存 | 服务端事务创建、重新计价和生成单号 |
| 支付 | 客户端模拟修改状态 | 微信支付下单、回调、查单、退款和对账 |
| 状态 | `pending` / `paid` | 支付状态与履约状态分离的状态机 |
| 商家作业 | 菜单编辑页 | 订单工作台、厨房看板、菜单和员工管理 |
| 运维 | 无集中日志 | 多环境、结构化日志、指标、告警和备份 |

## 3. 推荐的系统形态

```text
顾客小程序                    商家管理端（Web / 平板）
  浏览、下单、支付              接单、制作、菜单、员工、报表
          \                    /
           CloudBase API / 云函数
          /       |        |       \
     MySQL     云存储    微信支付    消息与定时任务
   业务数据     菜品图片   回调查单    超时关单、通知
```

建议分成三个产品界面，共用一个后端：

1. 顾客小程序
   - 保留当前 AppID 和 uni-app 工程能力。
   - 只保留扫码、商家品牌主页、菜单、购物车、结算、支付和订单页面。
   - 不再包含商家入口、演示数据重置和菜单编辑代码。

2. 商家管理端
   - 首选响应式 Web 管理台，适配电脑、横屏平板和手机浏览器。
   - 菜单编辑、员工权限、数据统计更适合大屏和键鼠输入。
   - 店内平板可以常驻“新订单 / 制作中 / 待取餐”工作台。

3. 商家小程序，可选
   - 只做移动接单、催单、售罄、订单状态变更等高频操作。
   - 等 Web 管理端稳定后再决定是否需要单独 AppID，不把它作为第一阶段前置条件。

这里的“顾客和商家分离”首先是代码、页面、身份和权限分离，不一定马上注册两个小程序。立即拆成两个 AppID 会增加认证、审核、发布和身份映射成本。

## 4. 后端和数据库选择

### 推荐方案

首个真实运营版本采用：

- CloudBase 云函数或 HTTP 云函数：承载登录、菜单发布、下单、支付和商家操作
- CloudBase MySQL：保存用户、门店、菜单、订单、支付和权限数据
- CloudBase 云存储：保存门店封面、菜品图片和导出文件
- CloudBase 环境：至少分开发环境和生产环境，上线前增加预发布环境

CloudBase 当前同时提供身份认证、文档型数据库、MySQL、云函数、云存储和 Web 托管。Ordio 的订单、员工、支付和报表关系较多，MySQL 比把所有内容塞入单个 JSON 文档更容易维护约束、索引和统计。

文档型数据库仍可用于低耦合数据，例如操作日志、异步任务或临时配置，但不建议把订单主数据拆成两套数据库。

### 为什么不能让小程序直接写核心表

小程序代码和请求参数都可以被查看或伪造。以下操作必须进入云函数或后端 API：

- 判断当前用户是否属于门店及其角色
- 读取最新菜单并重新计算价格
- 创建订单号和支付单号
- 扣减或释放库存
- 改变订单、支付和退款状态
- 发布菜单和管理员工
- 处理微信支付回调与主动查单

客户端只提交意图，例如菜品 ID、规格 ID、数量和桌台令牌。最终金额、门店、用户和订单状态由服务端生成。

### 何时改为自建后端

出现以下情况再评估 NestJS / Java 服务加独立 MySQL、Redis 和对象存储：

- 已经有独立运维团队和统一账号体系
- 需要接入多平台订单、ERP、供应链或复杂打印系统
- 需要跨云部署、私有化交付或大量长连接
- CloudBase 的配额、网络或成本经过真实监控后不再合适

首版不同时维护 CloudBase 和自建后端两套实现。

## 5. 建议的数据模型

所有业务表使用服务端生成的 ID，金额保存整数分，时间使用数据库时间。关键表使用 `created_at`、`updated_at`，需要保留历史的数据使用软删除或状态字段。

| 表 | 主要用途 | 关键约束和索引 |
| --- | --- | --- |
| `users` | 顾客和员工的统一用户主体 | `openid` 唯一，不向其他用户返回 |
| `stores` | 门店资料、营业状态和配置 | `status`、`owner_user_id` |
| `store_members` | 员工和门店角色关系 | `(store_id, user_id)` 唯一 |
| `tables` | 桌号、区域和桌码 | `table_token` 唯一且不可猜测 |
| `categories` | 菜单分类草稿 | `(store_id, sort_order)` 索引 |
| `dishes` | 菜品草稿、价格、图片和售罄状态 | `(store_id, category_id, status)` |
| `spec_groups` | 规格组、必选和选择数量 | `dish_id`、`sort_order` |
| `spec_options` | 规格选项、加价和可用状态 | `spec_group_id` |
| `menu_releases` | 每次发布的不可变菜单快照 | `(store_id, version)` 唯一 |
| `orders` | 订单主表、金额和状态 | 门店订单号唯一，按门店和时间索引 |
| `order_items` | 商品名称、价格、数量快照 | `order_id` 索引 |
| `payments` | 商户支付单、微信单号和支付状态 | `out_trade_no`、`transaction_id` 唯一 |
| `refunds` | 退款申请、金额和状态 | `out_refund_no` 唯一 |
| `order_events` | 订单状态变更时间线 | `(order_id, created_at)` |
| `media_assets` | 云文件 ID、尺寸、归属和状态 | `(store_id, type)` |
| `storefront_drafts` | 商家主页模板、主题令牌、区块配置和招牌菜 | `store_id` 唯一 |
| `storefront_releases` | 顾客端读取的不可变主页版本 | `(store_id, version)` 唯一 |
| `idempotency_keys` | 防止重复下单和重复写入 | `(scope, request_id)` 唯一 |
| `audit_logs` | 员工敏感操作审计 | `(store_id, created_at)` |

后续功能再增加：

- `inventory_items`、`inventory_events`：库存和变更流水
- `customer_profiles`、`member_points_ledger`：会员和积分流水
- `coupons`、`coupon_claims`：优惠券规则和领取记录
- `store_business_hours`：分日期营业时间和临时停业
- `notification_jobs`：订阅消息与失败重试

### 菜单版本

商家编辑的是草稿表。点击发布时，服务端在事务中完成校验并生成一份不可变 `menu_releases` 快照：

- 顾客读取门店当前 `published_menu_version`
- 历史订单保存当时的菜品、规格和价格快照
- 后续改名、改价或删除菜品不会改变历史订单
- 发布失败时不切换当前版本

## 6. 身份、角色和权限

### 顾客身份

- 使用微信身份建立 `users` 记录
- 顾客只能查看公开菜单和自己的订单
- 手机号、昵称和头像按业务必要性申请，不在首次进入时强制索取
- 购物车可以继续本地缓存，订单必须云端保存

### 商家身份

员工能登录不代表有门店权限。每个商家请求都由服务端读取 `store_members`：

| 角色 | 权限 |
| --- | --- |
| `owner` | 门店、员工、菜单、订单、退款、报表全部权限 |
| `manager` | 菜单、营业状态、订单和基础报表 |
| `cashier` | 接单、取消、收款状态查看和备注 |
| `kitchen` | 查看订单、开始制作、完成出餐 |

退款、员工管理和门店删除等高风险操作不能只通过前端隐藏按钮控制，必须服务端校验角色并写入审计日志。

### 数据权限

- 核心业务表默认禁止客户端直接写入
- 所有查询都带服务端确认的 `store_id`，不信任客户端传入的门店归属
- 云存储按门店和用途组织路径，上传后记录 `media_assets`
- 支付密钥、AppSecret 和数据库凭据只保存在云端环境变量或密钥管理中
- 开发、预发布、生产使用不同环境和不同数据

## 7. 订单与支付逻辑

订单履约状态和支付状态必须分开，避免“已支付”同时表示“已接单”或“已完成”。

```text
订单履约：
pending_payment -> placed -> accepted -> preparing -> ready -> completed
                       \-> rejected
placed / accepted -----> cancelled

支付：
not_pay -> success -> refunding -> refunded
    \----> closed
```

服务端规则：

1. 下单时根据当前发布菜单重新核对菜品、规格、价格、售罄状态和桌台。
2. 使用事务创建订单、订单项、事件记录和必要的库存预占。
3. 客户端生成一次性 `request_id`，重复请求返回同一订单，不重复创建。
4. 支付参数由服务端向微信支付申请，客户端只调用收银台。
5. 客户端支付成功回调不能直接把订单改成已支付。
6. 服务端验证支付通知；未收到通知时主动查单，以微信侧状态为准。
7. 回调和查单更新必须幂等，保存微信支付订单号和通知 ID。
8. 超时未支付订单由定时任务关闭并释放库存。
9. 退款由有权限的员工发起，保存退款单和状态变化。

微信支付官方要求商户先在服务端下单，再由小程序调起支付，并结合支付通知和主动查单确认最终结果。正式接入前还需要完成小程序认证、商户号申请和 AppID 绑定。

## 8. 桌码和就餐场景

桌码不再直接包含可修改的 `storeId`，建议使用：

```text
scene=tableToken_xxxxxxxxx
```

服务端通过令牌解析门店和桌台。令牌需要：

- 足够随机，不能从桌号推算
- 支持禁用和重新生成
- 服务端校验门店是否营业、桌台是否启用
- 订单快照保存桌号和区域

首版只做堂食。外带可以作为下一阶段增加 `order_type` 和取餐号；配送需要地址、配送范围、运费和履约系统，不和堂食首版混做。

## 9. UI 和交互优化

### 顾客小程序

保留当前米白、深色和橙色的品牌方向，但建立统一设计变量：

- 主色、成功、警告、错误和禁用色固定语义
- 统一 4 / 8 / 12 / 16 / 24 的间距层级
- 标题、正文、辅助文字和价格使用固定字号层级
- 所有点击区域满足触屏操作，不只依赖小号文字按钮
- 适配底部安全区、深色文字对比度和系统字体放大

页面调整：

| 页面 | 优化重点 |
| --- | --- |
| 扫码落地 | 展示门店、桌号、营业状态和网络异常恢复 |
| 菜单 | 吸顶分类、搜索、销量或标签、售罄态、图片渐进加载 |
| 规格弹层 | 已选摘要、必选提示、数量、单品备注和实时价格 |
| 购物车 | 展开编辑、包装费或优惠明细、最低消费提示 |
| 结算 | 桌号、人数、备注、餐具、金额明细和支付方式 |
| 订单详情 | 状态时间线、预计时间、催单入口、再次点单 |
| 订单列表 | 进行中和历史订单分组、空状态和分页 |

需要补齐骨架屏、空数据、弱网、超时、重复提交、菜单已更新和门店休息等状态，避免所有异常都只弹一个 Toast。

### 商家管理端

默认首页不是菜单编辑，而是订单工作台：

- 新订单、已接单、制作中、待取餐四列或四个筛选页
- 新单声音和醒目提示，可以单独关闭
- 大按钮完成接单、拒单、开始制作和出餐
- 显示桌号、下单时间、等待时长、备注和支付状态
- 并发更新时提示“订单已由其他员工处理”，不覆盖新状态

其他模块：

- 菜单：分类、菜品、规格、批量售罄、草稿预览和发布记录
- 门店：营业时间、临时停业、桌台和二维码
- 员工：邀请、角色、停用和操作记录
- 订单：搜索、筛选、取消、退款和导出
- 数据：销售额、订单量、客单价、热销菜品和退款率

### 模板化主页搭建

主页搭建是 Ordio 区别于普通扫码点餐工具的核心能力，不再只把店名、封面和菜单拼成固定页面。商家从经过适配的餐饮模板开始，通过有限但明确的配置完成品牌表达，不需要设计或前端开发能力。

首个版本包含：

- 三类基础模板：暖意食堂、清新自然、醒目招牌；模板决定版式、留白、圆角和内容节奏
- 品牌令牌：主色、封面、短标、标题、副标题和行动按钮文案
- 标准区块：门店公告、招牌推荐、品牌故事、到店信息；支持显隐和排序
- 招牌菜选择：从当前菜单选择主页推荐菜，不重复维护商品和价格
- 草稿与发布分离：商家编辑草稿，顾客只读取不可变发布版本
- 多端预览：至少提供手机尺寸预览，Web 管理端阶段补充平板预览

首版不做自由画布、任意坐标拖拽和商家注入自定义代码。这类能力在小屏上难操作，也容易造成审核、性能和视觉质量问题。创新点放在“模板骨架 + 可编排业务区块 + 菜单数据联动 + 安全发布”上，后续再根据门店行业、菜品结构和经营时段提供模板推荐、节日主题包和区块组合建议。

主页配置需要独立版本号。发布时服务端校验模板和区块白名单、资源归属、招牌菜是否属于当前门店以及文案长度，再生成 `storefront_releases` 快照。模板后续升级不能直接改变已经发布的商家主页。

## 10. 功能优先级

### P0：单店真实运营基础

- 顾客端与商家端代码和入口分离
- 模板化门店主页、区块编排、招牌菜联动和独立版本发布
- CloudBase 开发 / 生产环境
- 微信用户身份、员工角色和门店权限
- MySQL 结构、迁移脚本、索引和种子数据
- 云存储图片上传与回收
- 桌台和桌码
- 云端菜单草稿、版本发布和售罄
- 服务端创建订单、重新计价和幂等处理
- 商家订单工作台和完整订单状态
- 微信支付、回调、查单、关单和基础退款
- 结构化日志、错误追踪、备份和恢复演练

P0 完成前，不引入积分、优惠券和推荐算法。

### P1：门店效率

- 订阅消息或其他合规通知方式
- 外带和取餐号
- 单品备注、整单备注、餐具和人数
- 简单库存与一键售罄
- 厨房看板和打印适配接口
- 营业时间、临时停业和自动关店
- 订单搜索、导出、退款和日结报表

### P2：复购与经营

- 会员资料、积分流水和储值可行性评估
- 优惠券、满减和活动价
- 再次点单、收藏和常点菜品
- 销量、客单价、时段和菜品分析
- 多门店切换和总部菜单模板
- 行业模板包、节日主题、主页区块组合建议和版本回滚

### P3：平台化

- 多商户入驻和门店审核
- 套餐计费、商户结算和平台运营后台
- 开放 API、打印机、ERP 和供应链集成

## 12. 从当前代码迁移

不建议推倒重写页面。按数据层逐步替换：

1. 保留现有 `repository.js` 的调用方向，先定义清晰的 repository 接口。
2. 将本地实现改名为 `local-repository`，仅用于演示和自动化测试。
3. 新增 `cloud-repository` 或 `api-client`，页面不直接调用 `wx.cloud.database()`。
4. 将主页配置拆成草稿和发布适配器，顾客端只读取发布版本。
5. 将价格校验和 `createOrder` 移到云函数，前端只保留展示计算。
6. 商家页面迁移到独立管理端，顾客包删除对应路由和代码。
7. 图片从本机路径迁移为云文件 ID，数据库只保存资源引用。
8. 本地购物车可以保留；登录后可选同步，但服务端下单仍重新校验。
9. 当前演示数据只作为开发种子，不迁移为生产订单。

建议的目标目录：

```text
apps/
  customer-mini/       顾客 uni-app
  merchant-admin/      商家 Vue 管理台
  merchant-mini/       可选，后续增加
services/
  cloudfunctions/      登录、菜单、订单、支付、通知
packages/
  contracts/           接口类型、状态和校验规则
  domain/              金额、菜单、订单等纯业务逻辑
infra/
  migrations/          MySQL 迁移
  seeds/               开发种子数据
docs/
```

是否改成 monorepo、npm workspaces 或其他包管理方式，需要先用 uni-app 构建验证，不能只为目录整齐一次性更换工具链。

## 13. 环境、测试和运维

### 环境

- `dev`：开发数据，可重置
- `staging`：接近生产配置，用于体验版和回归
- `prod`：真实用户和支付数据，严格控制权限

环境 ID、支付商户号和密钥不写入仓库。生产数据库禁止从本地脚本随意重置。

### 自动化测试

- 纯业务单元测试：金额、规格、购物车键、状态迁移、权限判断
- 数据库集成测试：事务、唯一约束、并发下单和回滚
- API 契约测试：正常请求、无权限、重复请求和参数错误
- 小程序自动化：扫码落地、点餐、支付前流程和订单查询
- 商家端 E2E：接单到出餐、并发处理、菜单发布
- 支付测试：开发环境使用受控的支付适配器，正式环境进行小额真实联调
- 安全测试：越权访问、伪造门店 ID、重复回调和恶意数量

### 监控

- 每个请求记录 `requestId`、`userId`、`storeId` 和 `orderId`
- 监控云函数错误率、耗时、数据库慢查询和支付回调失败
- 对新订单积压、支付状态不一致、库存负数和退款失败告警
- 每日自动对账，记录微信支付金额和本地订单金额差异
- 定期备份并实际演练恢复，不只确认“已有备份”

## 14. 分阶段交付

工期需要在账号、支付资质和商家端形态确定后再估算，下面按可验收结果拆分。

### 阶段 A：架构和数据基础

- 确认单店试点范围和商家端形态
- 开通 CloudBase 开发环境
- 完成数据库设计、迁移、种子和权限模型
- 建立 API 契约、错误码和请求日志

完成标准：开发环境能登录，能区分顾客和员工，跨设备读取同一门店菜单。

### 阶段 B：菜单和桌码

- 云端店铺、桌台、菜品、规格和图片
- 云端主页草稿、模板配置、区块编排和不可变发布版本
- 商家独立登录与菜单发布
- 顾客桌码落地、商家主页和发布菜单读取

完成标准：商家设备发布主页或菜单后，另一台顾客设备立即读取；未发布草稿不会泄漏，模板升级不会改变历史发布版本。

### 阶段 C：真实订单

- 服务端订单创建、快照、事务和幂等
- 商家订单工作台
- 履约状态、取消和售罄处理

完成标准：两台设备并发下单不会重复或串店，商家状态变化能被顾客看到。

### 阶段 D：支付和通知

- 微信支付商户配置
- 预支付、收银台、回调、查单、关单和退款
- 合规的订单通知

完成标准：支付结果以服务端为准，重复通知不重复记账，漏通知可通过查单恢复。

### 阶段 E：UI、稳定性和试营业

- 顾客端视觉和异常状态重做
- 商家端平板操作优化
- 性能、弱网、日志、告警、备份和恢复
- 真实门店小范围试营业

完成标准：连续营业测试期间无丢单、错价、跨店越权和不可恢复的支付状态。

### 阶段 F：经营功能

只根据试营业数据选择 P1、P2 功能，不按功能清单全部开发。

## 15. 开工前需要确认的业务选择

| 问题 | 推荐默认值 |
| --- | --- |
| 首个版本单店还是平台 | 单店试点，表结构支持多店 |
| 商家端形态 | 响应式 Web 管理台，后补移动接单端 |
| 主页搭建范围 | 模板、品牌令牌和标准区块编排，不做自由画布 |
| 首发场景 | 堂食桌码，不含配送 |
| 支付方式 | 有商户资质则接微信支付；否则先到店支付但保留支付表 |
| 库存 | 首版做售罄和简单日库存，不做原料 BOM |
| 打印机 | 预留订单事件接口，型号确定后接入 |
| 会员营销 | P0 完成后再排期 |
| 云端方案 | CloudBase 云函数、MySQL、云存储 |

## 16. 真实运营版完成标准

- 顾客无法进入或调用商家功能
- 员工不能访问未授权门店
- 菜单、订单和状态可以跨设备恢复
- 每个商家可以发布独立品牌主页，顾客看不到未发布草稿或其他门店配置
- 客户端改价格或门店 ID 不会影响服务端结果
- 重复点击下单和重复支付通知不会产生重复订单或重复记账
- 菜单改价后历史订单保持原快照
- 支付状态由通知和查单确认，不依赖客户端成功回调
- 商家可以完成接单、制作、出餐、取消和退款流程
- 生产环境有日志、告警、备份和恢复记录
- 真机弱网、前后台切换和并发操作通过回归
- 至少完成一次真实门店连续试营业验证
