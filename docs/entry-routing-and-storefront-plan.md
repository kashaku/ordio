# Ordio 入口、桌码与产品拆分方案

## 当前状态

| 能力 | 当前实现 | 结论 |
| --- | --- | --- |
| 顾客入口 | 小程序首页扫码；开发者工具可带参数打开扫码页 | 已有入口 |
| 商家入口 | 独立 Web 管理端已建立登录门禁、经营概览和主页搭建首屏 | 开发预览可用，正式身份接口待接入 |
| 顾客与商家区分 | 顾客首页不展示商家按钮，但尚无登录和服务端角色校验 | 只完成界面隔离，未完成权限隔离 |
| 桌台令牌 | 本地 `tables` 数据、随机 `tableToken`、启停和轮换 | 已完成本地骨架 |
| 扫码解析 | 支持 `scene=t=<tableToken>`、`tableToken` 和旧 `storeId` | 已完成兼容解析 |
| 二维码图片生成 | 未接入微信服务端小程序码能力 | 尚不支持正式生成 |
| 跨设备同步 | 数据仍在 `uni.setStorageSync` | 尚不支持 |

旧 `storeId` 入口只用于迁移兼容，不能作为正式桌码。它可被猜测，也没有桌号、启停或轮换能力。

## 目标入口

### 顾客

顾客继续使用当前微信小程序 AppID，入口按优先级分为：

1. 扫桌台小程序码：直接打开顾客入口页，`scene` 只携带不可猜测的桌台令牌。
2. 在小程序内点击“扫码进入门店”：调用扫码能力，解析同一种桌台令牌。
3. 分享或门店主页入口：可以浏览主页和菜单，但未识别桌台时不能直接提交堂食订单，需要补扫桌码。

统一链路：

```text
scene / 扫码内容
  -> 入口解析
  -> 服务端解析 tableToken
  -> 校验桌台、门店、营业状态
  -> 门店主页
  -> 菜单
  -> 结算时再次校验 tableToken
```

客户端只保存和传递令牌，不根据令牌自行推断门店，也不信任 URL 里的 `storeId` 作为订单归属。

### 商家

生产环境采用响应式 Web 管理端，入口为独立管理域名，不在顾客首页暴露商家按钮。

```text
商家 Web 登录
  -> 建立用户身份
  -> 服务端查询 store_members
  -> 选择有权限的门店
  -> 订单工作台 / 主页搭建 / 菜单 / 桌台 / 员工
```

登录成功不等于拥有门店权限。每次商家请求仍由服务端检查 `store_members`，前端路由守卫只负责体验，不能代替权限校验。

独立商家 Web 管理端位于 `apps/merchant-admin`，当前已经具备单独登录页、权限路由、经营概览和主页搭建预览。`pages/merchant/index` 只用于迁移期功能核对；Web 管理端覆盖菜单和桌台后，从顾客小程序构建中删除该页面和全部商家 repository 方法。是否增加商家小程序，在真实门店验证移动接单需求后再决定。

## 如何区分顾客与商家

不使用“同一个首页让用户自己选角色”，也不接受 `role=merchant` 这类客户端参数。

| 维度 | 顾客 | 商家 |
| --- | --- | --- |
| 产品入口 | 微信小程序、桌台码 | 独立 Web 管理端 |
| 身份 | 微信身份 | 管理端登录身份 |
| 门店归属 | 由桌台令牌解析 | 由 `store_members` 查询 |
| 可访问数据 | 已发布主页、已发布菜单、本人订单 | 被授权门店的草稿、订单、员工和配置 |
| 写权限 | 购物车意图、下单、本人订单操作 | 按角色执行接单、发布、桌台和员工操作 |

如果以后增加商家小程序，也使用单独入口和角色校验，不复用顾客首页的可见按钮。

## 桌码生成与生命周期

### 数据

`tables` 至少包含：

- `id`、`store_id`、`name`、`area`
- 唯一且不可猜测的 `table_token`
- `enabled`、`created_at`、`updated_at`
- `qr_file_id`、`qr_generated_at`

令牌由服务端使用安全随机数生成。令牌更新后旧码立即失效，订单只保存桌台 ID、桌号和区域快照，不依赖后来可能变化的桌台名称。

### 生成流程

1. 有桌台管理权限的员工创建桌台或更新令牌。
2. 服务端提交事务，保存新令牌并使旧令牌失效。
3. 云函数调用微信服务端的小程序码能力，目标页固定为顾客入口页，`scene` 只放短令牌参数。
4. 生成的图片写入云存储，`tables.qr_file_id` 保存资源引用。
5. 商家管理端提供预览、下载和批量打印；不把 AppSecret、接口凭据或生成请求放进小程序前端。

微信服务端接口、scene 长度、调用额度和账号资质在真正接入时必须重新核对当期官方文档。当前代码只完成令牌和解析链路，没有把占位图片称为正式桌码。

### 异常边界

| 情况 | 顾客结果 | 商家操作 |
| --- | --- | --- |
| 无效令牌 | 显示“桌码无效或已经更新”并重新扫码 | 检查桌台或重新下载新码 |
| 桌台停用 | 阻止进入点餐流程 | 重新启用后生效 |
| 门店休息 | 可展示主页，禁用下单并显示营业时间 | 修改营业状态 |
| 菜单未发布 | 主页可展示，菜单显示未发布状态 | 发布菜单 |
| 弱网或超时 | 保留重试入口，不跳到错误门店 | 查看服务端日志和请求 ID |
| 令牌被复制 | 服务端仍按同一桌台处理；高风险门店可定期轮换 | 更新令牌并替换桌牌 |
| 更新令牌后旧码被扫 | 明确提示旧码失效 | 确认现场是否仍放置旧桌牌 |

## 个性化主页能力规划

### P0：可运营基础

- 模板、品牌色、封面、首屏文案
- 公告、招牌菜、品牌故事、到店信息区块
- 区块显隐和排序
- 草稿、手机预览、发布版本和发布审计
- 素材归属校验、文案长度和区块白名单

### P1：更丰富但仍可控

- 营业状态、优惠横幅、套餐、图片画廊、视频封面
- 区块样式变体和间距密度
- 节日主题包、定时发布和版本回滚
- 手机、平板预览以及分享卡片配置
- 无障碍对比度和图片尺寸检查

### P2：经营联动

- 按早餐、午餐、晚餐切换推荐区块
- 售罄后自动替换招牌菜
- 根据门店类型推荐模板和区块组合
- 主页访问、菜单点击和下单转化统计
- 多门店复制模板，允许门店覆盖部分内容

### 边界

- 不做任意坐标自由画布，避免手机编辑困难和页面失控。
- 不允许商家注入 HTML、JavaScript、WXSS 或外部脚本。
- 区块只能引用本门店已审核素材和已发布业务数据。
- 模板升级不直接修改商家已发布版本。
- 顾客端永远读取发布快照，不读取编辑中的草稿。
- 自动推荐只生成建议，不能绕过商家确认直接发布。

## 拆分和实施顺序

### 阶段 A1：入口与桌台基础

- 统一入口解析，兼容外部小程序码和小程序内扫码
- 本地 `tables`、安全令牌、启停、轮换和订单桌台快照
- 补齐无效、停用、旧码和无桌台边界

完成标准：有效桌码进入正确桌台；停用和旧令牌不能下单；订单记录正确桌号。

### 阶段 A2：云端身份和数据

- CloudBase 开发环境
- 微信登录、用户、员工和 `store_members`
- MySQL 迁移、种子、索引和 API 契约
- 云端 table token 解析，关闭客户端对核心表的直接写入

当前进度：`ordioApi` 已部署到开发环境 `cloud1-d4gl08nvu64e07107`，`users`、`store_members`、`stores`、`tables` 集合及首批索引已经创建。下一步完成真实微信身份、试点门店种子数据和云端桌码联调；菜单、主页和订单暂未切换业务数据源。后续只保留一套正式数据源，不同时维护云数据库和 MySQL 两套业务实现。

完成标准：两台设备读取同一门店数据，顾客无法调用商家接口，员工不能跨店。

### 阶段 B1：正式桌码

- 云函数生成小程序码并上传云存储
- 商家端桌台创建、启停、更新令牌、下载和批量打印
- 二维码生成日志、失败重试和旧码失效提示

完成标准：商家生成桌码后，未安装或未打开小程序的顾客也能从微信扫码进入正确桌台。

### 阶段 B2：产品拆分

- 创建响应式商家 Web 管理端
- 迁移主页、菜单、桌台和员工管理
- 顾客构建删除商家路由、商家组件和商家写接口

完成标准：顾客包中不存在商家工作台代码；商家管理端权限由服务端校验。

当前进度：响应式管理端骨架、登录门禁、经营概览和主页模板实时预览已完成。开发预览会话只存在于 Vite 开发模式，生产构建不提供本地绕过；下一步接入正式商家登录和 `store_members`，再迁移菜单、桌台及主页云端保存发布。

### 阶段 C：真实订单与支付

- 服务端重新计价、幂等下单和桌台快照
- 商家订单工作台和履约状态机
- 微信支付、回调、查单、关单、退款和对账

完成标准继续沿用 `production-roadmap.md` 的真实运营验收要求。
